旧代码的故障放大路径已用真实 `app.run` 与构造响应复现：主线程同步兜底连续超时，会不断把我的活动重启时间后移，并使列表读者等待主线程先成功取数才能重新启动。因此不能用“后台普通失败约 0.1 秒重建”概括旧版所有错误分支。

仍保留学校明确要求的共享等待，以及认证失效、结构异常和无明确等待值的 502–504 的相应恢复/退避。提交串行、我的活动数据可靠性、冲突检查、待确认计数及按 ID 确认不放宽。等待尚未返回的我的活动线程不算查询失败，也不增加有效缺席核对次数。

## 失败诊断

`Client.request` 增加仅本地的 `request_failed`：

- `reader`：main、activities、history 或通用 background；只读克隆继承诊断回调，保持会话独立。
- `endpoint`：活动列表、我的活动、验证码、提交、取消的白名单端点名；其他路径记 `other`，不保存 URL 或参数。
- `reason`、`stage`、`exception_type`：安全原因码、失败阶段与异常类型，不保存异常原文。阶段为 dns/tcp/tls/headers/body；无法归入这些阶段的错误记 request，部分分支异常已经过归一化。
- `budget_seconds`、`duration_seconds` 和各阶段的 `*_seconds`；未执行或未细分阶段为 null，复用连接没有新的建连耗时。TLS 计时扣除已细分的 DNS/TCP。

`opening_snapshot_missing` 与 `opening_history_missing` 增加 `reader_in_flight`、`reader_request_started_at`。它们仍按失联期去重；`background_reader_stopped` 仍按 reader 每五秒节流。完整诊断不进入终端、事件、邮件或网页。
