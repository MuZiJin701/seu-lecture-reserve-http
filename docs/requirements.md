# 讲座预约需求

截至 2026-10-30 的当前有效规则。本文汇总已确认需求；文末实施记录保留历史变化，不覆盖正文的当前规则。实现和真实验收分别见[使用指南](usage.md#验收记录)，术语见 [GLOSSARY.md](../GLOSSARY.md)。

## 多账号与 Web 改造

2026-10-30 经逐轮澄清及 FastAPI 修订，用户已整体确认以下方案与具体默认；现已实现 Web 控制台与多账号进程隔离，离线证据见[HTTPS 版本验收](acceptance/2026-10-30-web-offline.md)与[本轮 HTTP 简化验收](acceptance/2026-10-30-http-console.md)，部署见[Web 指南](web.md)。真实学校多账号、Linux 部署和长期运行仍待分别验收；下文预约规则逐账号适用。本轮单页改版及管理员登录以 [新版需求](console-redesign.md)、[ADR-0010](adr/0010-configured-admin-login.md) 和 [ADR-0011](adr/0011-local-reservation-display-snapshot.md) 为准；保留 ADR-0008 的 HTTP 与文件权限取舍。离线证据见[改版验收](acceptance/2026-10-30-console-redesign.md)。

### 使用范围与账号身份

- 仅由本人或少数可信操作者在可信局域网／VPN 内使用的管理台，不开放注册或多人自助。管理员在服务器 `.env` 中配置，全部管理员共享学校账号及完整操作权限；配置启动时读取、增删或改密重启生效，见 [ADR-0001](adr/0001-single-admin-multiple-school-accounts.md) 与 [ADR-0008](adr/0008-trusted-environment-http-no-login.md)。
- 操作者可新增、查看、配置、启动、停止、删除多个学校账号。一卡通号唯一且添加后不可修改，显示名称、密码和选项可改；不能把任务或 Cookie 转给另一账号。见 [ADR-0004](adr/0004-immutable-school-account-identity.md)。
- 10 个账号仅为首期并发验收目标，不设启动硬上限，也不增加排队机制；实际容量须测量，不能用已有单账号实测代替。
- 学校密码与登录 Cookie 本地明文保存，不做应用层加密或配置解密密钥；不限制文件权限，凭据仍不得进入仓库、日志或网页响应，网页仅允许替换学校密码、不返回原文。见 [ADR-0005](adr/0005-local-plaintext-school-credentials.md)，已取代第二轮的 [ADR-0002](adr/0002-encrypted-school-credentials.md)；文件权限边界由 [ADR-0008](adr/0008-trusted-environment-http-no-login.md) 取消。

### 并发、认证与生命周期

- 每学校账号一个独立工作进程，会话、状态目录、`task.lock`、Cookie、人工认证等待及退避分别隔离；同账号内部继续共享现有服务端等待，不因某账号的认证等待或退出阻塞其他账号。见 [ADR-0003](adr/0003-per-account-worker-process.md)。
- 同一学校账号允许并发会话：账号身份锁与 `locks/` 目录已移除，CLI、Web 或不同机器不再因同号互斥；单账号、单机、约 4 分钟只读实测未观察到会话互踢或后登录被拒，见[并发登录验证](acceptance/2026-10-30-concurrent-login.md)与 [ADR-0009](adr/0009-concurrent-sessions-and-locks.md)。该结论不能外推开抢期、多 IP、三个以上会话或提交链路；重复预约仍由状态目录锁与待确认保护阻止。删除在检查状态文件前先取得该账号 `task.lock`；CLI 正常启动在加载 OCR 前取得同一把锁并复查账号仍存在且非删除中，删除与启动准备互斥，账号已删除时不进入引擎或重建任务。
- 保留现有预约引擎、选听目标及轮询频率；429／`Retry-After` 等仍是防御性处理，已有实测未观察到业务接口限流。多账号请求量及资源开销另行验收。
- 新增账号先保存，手动启动；服务重启恢复此前在运行的账号，已停止、任务完成或因不可自动恢复错误停止的账号保持停止。关闭网页不停止后台任务。
- 外部 CLI `--account` 持锁运行同一账号时，管理台的启动、保存、停止与删除均返回 `state_in_use`，不伪造停止成功、不写入配置或进入自动重启预算与告警；停止与改配置须在原终端完成。账号运行中保存配置时，管理台在持有该账号检查点锁的临界区内写入；CLI 正常启动在取得锁后重新读取筛选、学校密码和邮件配置，避免检查与写入之间被 CLI 插入而出现“数据库新配置、运行旧配置”。配置已写入后若 CLI 抢先取得锁，保存返回已保存结果、管理台跳过本次重启并显示 CLI 正在运行，不将已保存报为失败，也不进入重启预算或告警。
- 工作进程意外退出后有限次数自动重启，持续失败标记异常并按该账号通知配置告警；密码明确错误、状态损坏和等待人工认证不反复重启。每次恢复先加载原任务，核对待确认提交。
- 网页按账号显示人工认证状态，支持主动发送／重发短信和输入验证码，沿用现有短信冷却。未知挑战显示原因并等待，不替用户自动完成不支持的认证。
- 运行中账号保存新配置后只安全重启该账号，沿用原任务与待确认保护；已停止账号只保存。停止请求须中断等待并等待工作进程退出，不能把提交中的状态直接丢弃。
- 删除前先停止账号；存在待确认提交或保护占位时，先完成核对再允许删除。删除期间持有该账号状态目录锁，覆盖待确认检查至文件清理全程，拒绝并发 CLI 写入新的待确认记录。删除本地凭据、配置及运行记录，不取消学校已有预约。

### 每账号选项与通知

- 提供类别、校区及线上／线下筛选；已纳管账号不再按标题限制，设备信任、预热、验证码预取、后台历史刷新、开抢对齐和成功通知统一开启并隐藏开关；选听目标仍为现有八场及三类要求，不增加可调目标或轮询频率。
- SMTP 发信账号继续共用服务器 `.env`；每学校账号可单独填写一个收信邮箱，填写后自动开启重大告警和每次成功通知，不显示邮件开关。留空关闭该账号邮件；启用通知必须提供有效收件人，不能回退为公共发信邮箱。
- 网页提供测试邮件；仅发送当前重大告警及预约成功通知，不新增日报、目标完成或恢复邮件，保留 SMTP 接受与收件箱送达的区别。
- 账号启用邮件时，共用发信配置缺失或未通过现有配置校验就阻止该账号启动；`--check` 与 `--resolve-pending` 不发送邮件，不因共用发信配置无效而失败；未启用邮件的账号仍可运行。运行中发送失败记录并提示，不改变预约结果或触发重复预约。

### 页面与部署

- 中文管理台，参考 Wandor / motionsites 的浅色自然静态背景、磨砂玻璃、大圆角和黑色主按钮，保留现有前端技术栈，兼顾手机和电脑；移除宣传区和左侧导航，使用 Python 绘制的书页与时钟纯图案 Logo。卡片末尾始终有新增入口，选中后显示配置与预约清单。
- 提供全局总览和每账号运行阶段、选听进度、候选筛选原因、下次检查时间、安全事件及邮件状态。完整 `diagnostics.jsonl` 仍留在服务器，不直接在网页展示；成功邮件的既有可观测性限制仍须如实显示。
- 已确认 FastAPI＋普通 HTML/CSS／原生 JavaScript，浏览器定时读取状态；SQLite 保存账号目录及选项，每账号沿用现有任务 JSON 和恢复逻辑。单个 Web 管理进程负责账号生命周期，避免多个管理器重复启动同一账号。方案取舍见 [ADR-0006](adr/0006-web-control-and-local-state.md)。
- 使用 uv＋systemd 部署在 Linux 服务器；管理台明文 HTTP，默认监听 `0.0.0.0:8080`，不使用 TLS 证书、反向代理或证书准备／续期流程，端口与配置文件可用 `--config` 指定。见 [ADR-0008](adr/0008-trusted-environment-http-no-login.md)（取代 [ADR-0007](adr/0007-direct-https-without-reverse-proxy.md)）。
- FastAPI 由 Uvicorn 承载，固定一个 Web worker，关闭开发热重载；账号工作进程继续独立并发。预约循环不放进 async 路由或请求后台任务，避免阻塞事件循环或绑到单次请求生命周期。管理台提供管理员登录，固定 12 小时会话、多端并存，退出不停止预约，服务重启后重新登录；登录限速只统计失败尝试（每来源每分钟 5 次、全局每分钟 100 次），并发请求先原子预留校验名额再计算哈希，成功登录清除该来源记录，超限返回带 `Retry-After` 的 429；浏览器写操作校验会话 CSRF，非 GET 的 `/api/*` 仍校验 Origin（仅浏览器来源）与 `Content-Type: application/json`，并按实际接收字节累计限制请求体不超过 64 KiB（不只信任 `Content-Length`，分块传输同样受限），响应保留 CSP、`no-store`、`nosniff` 与 Referrer-Policy，不设置 HSTS。这些校验不是认证，不能替代网络边界。

### 兼容与验收

- 保留现有 CLI（含不带 `--account` 的旧单账号运行方式）；Web 用 `--account` 管理已纳管账号。不再检测或导入旧的单账号任务文件，新部署从空数据根目录开始。同一数据根目录由 `manager.lock` 限制一个 Web 管理服务，每个账号状态目录由 `task.lock` 限制一个写者；不再有 CLI／Web 同号身份锁。见 [ADR-0009](adr/0009-concurrent-sessions-and-locks.md)。
- 同一学校账号并发会话已实测可行；不因此推断开抢期、多 IP 或三个以上会话的行为。重复预约仍由状态目录锁与待确认保护阻止；不同状态目录的两套任务无法互相发现。
- 先用构造学校响应、临时目录与替代认证／邮件完成 10 账号离线验收：状态及 Cookie 隔离、重复启动、短信路由、单账号阻塞及故障、恢复与停止、配置重启、删除保护、HTTP 启动与浏览器防护和收件人路由。离线不访问学校、不提交真实预约、不发真实邮件。
- 同时验证匿名接口被拒绝、会话到期及退出、管理员配置、版本冲突、预约快照和浏览器 Origin / CSRF 防护、敏感字段不回显、表单校验与状态变更保护、手机布局、减弱动态效果偏好，并测量进程／OCR 的资源占用。真实学校登录、并发查询、开抢收益、预约和长期运行仍需分别授权与验收。
- 中英文 README、Web／CLI 使用指南、配置样例和部署说明同步维护；实现完成与真实验收分别记录，不用离线构造结果证明学校可用性。

### 已确认的具体默认

- 意外退出采用最多连续三次自动重启、间隔五秒；稳定运行十分钟后重置连续重启计数，人工启动开启新一轮恢复预算。已明确不可自动恢复的错误不进入此预算。
- 页面默认每两秒更新状态，不增加学校查询请求；实际可见新鲜度仍包含既有健康快照合并写入延迟。
- 生产 ASGI 选 Uvicorn，与 FastAPI 配套，替代此前 Flask／Cheroot 候选；管理台明文 HTTP、配置的管理员登录、无证书配置，不提供 TLS／HTTPS 降级切换；服务更新后按既有恢复语义安全重启。

## 产品范围

- 少数同等权限管理员共同管理多学校账号的讲座预约工具，每账号在管理台内只允许一个工作进程；主要面向 Linux 服务器，兼容 Windows 离线检查及 CLI。访问学校系统使用通过证书校验的 HTTPS；管理台为本地 HTTP、需要管理员登录，仅部署在可信局域网或 VPN。
- 目标固定为至少选听八场人文与科学素养系列讲座，其中法律、艺术、心理健康各至少一场；“SEU咖啡间”系列沙龙活动仍可按配置预约，但不计入目标；测试活动及购票公告不预约、不计数。依据学校记录统计，不要求手工维护次数，也不代替学院最终认定。
- 不区分年级，不提供三场目标、自定义次数、考核截止日、个人日历或跨机器协调。无候选时持续等待，直到实际达标或用户停止。
- 学校凭据、票据和完整个人活动记录留在仓库与日志之外；不自动取消预约、签到、评价或反馈。

## 目标统计与冲突

- 从学校“我的活动”读取进度，按活动 ID 去重；学校标记已打卡、未违约且未取消的四类系列讲座才可计为已选听。
- 按 2026-10-28 用户提供并确认的最新公告说明，沙龙既不计已选听，也不占待参加目标缺口，包括全部已有历史及已确认的本地占位；7 场正式讲座加 1 场沙龙不算达标。已完成任务启动后重新核对，不足时恢复补约；不删除学校记录或自动取消沙龙，已有有效沙龙预约及占位仍参与时间冲突保护。已知沙龙的打卡/违约结论不影响目标统计，已有预约状态、活动时间等冲突检查仍须可靠。
- 有效且尚未结束的待参加预约可占用目标缺口；已选听加待参加覆盖总量和必需类别后暂停新增，继续核对。只有已选听本身达标才结束，预约一场成功后继续执行。尚未结束的预约缺少打卡/违约字段时按“未参加、未违约”处理并计入待参加。
- 已结束记录若学校尚未给出可读考勤结果，不计为已选听、不计入待参加，也**不暂停、不阻塞**其他讲座预约；学校之后回填打卡结果时，下一次扫描自动计入。学校可能约 24 小时后才给出线上讲座结果，程序不依赖也不等待该回填。
- 取消或学校确认违约后补足；所选记录已经结束但尚未登记打卡或违约时不再等待学校确认，继续预约其他讲座。
- 未知状态或类别、矛盾重复记录、已提供总数不一致时暂停新增。没有分页信息或总数不能证明全历史完整，证据见[接口调查](completion-records.md)。
- 旧版已确认占位缺少类别时，优先用本轮已有活动列表或历史补齐，不增加探测请求；仍不能确定类别时保留占位并暂停新增，不能漏计该预约。旧待确认记录缺少起止时间时保留待确认，不在无法建立时间占位时恢复提交。
- 新预约与学校全部有效预约检查冲突，区间重叠及首尾相接均算冲突；已有预约状态、时间或列表完整性不明时暂停提交。
- 不同 ID 的已有记录重叠时，只为本地计数选择互不冲突的记录：优先已打卡，再优先补齐缺少的必需类别，然后按结束时间较早、活动 ID 排序；每次选择后更新缺口并排除冲突项。不承诺全局最多场数，链式重叠可选择互不冲突的多场。
- 该选择不修改学校记录，不把未选记录自行标为违约；未选的有效预约仍用于拦截新预约冲突。

## 候选筛选

- 旧单账号 CLI 支持完整标题、类别、校区、线上线下开关和冲突筛选；已纳管账号清除标题限制，保留其余筛选。标题列表非空时完整匹配，空列表不限制；指定标题仍受其他条件约束，同名活动按不同 ID 处理。
- 默认允许线上，线下只允许明确配置的校区；空校区列表不约线下。默认类别含心理、法律、艺术、其他及沙龙五类，名称见 [.env.example](../.env.example)；沙龙是否启用由类别配置控制，继续受标题、校区、线上线下、冲突及原有目标缺口预约策略约束。沙龙成功不减少正式讲座缺口，不设独立沙龙次数目标；正式讲座已选听加待参加覆盖目标时暂停全部新增，实际选听达标后任务结束。不增加日期范围、每日可用时段或时长筛选。
- 列表中类别非空、有效且明确不在启用类别内时提前排除，不要求其余讲座字段完整。类别缺失或异常、目标类别记录仍严格校验；此例外不适用于已有预约及目标统计。
- 非目标类别诊断保留可用标题和预约时间；标题缺失显示空字符串，无法解析的预约时间显示未知。其他正常记录按首个命中的筛选原因解释，不把未知结构当作空列表。
- 目标讲座须校验发布状态、预约时间窗和明确的授课方式；未开放时也校验。起止时间无法解析则跳过该候选，资格与名额以学校活动列表的已约人数／总人数判定及提交后按活动 ID 核对为准。
- 候选同 ID 且内容一致时只处理一次，矛盾候选暂停本轮提交。优先补齐必需类别并为其预留缺口，再按配置类别顺序、线上优先、开始时间较早排序，最后按 ID 固定顺序。
- 已有记录导致必须超过八场才能满足类别时，仅补必要类别。标题列表不表示优先级，筛选配置不排除历史记录的目标统计。

## 认证、轮询与提交

秒历史缓存＋主线程同步刷新。同时保留已知且未结束的开抢窗口，最新列表合法但暂时为空或缺少目标时仍按已知窗口维持快轮询，提交仍只依据最新有效列表。后台活动列表线程不可用而回退为同步查询时，开抢窗口内相邻同步列表查询至少间隔 0.25 秒（`FAST_SYNC_MIN_INTERVAL`）；窗口内首次回退不额外延迟，普通扫描与历史查询不受影响，回退仍现场取数、不复用旧行。目的是避免线程持续失败时 0.10 秒快循环变成同步请求突发；代价是线程确实不可用时可能错过约 0.15 秒的预热／预取窗口而退回现场取图。429/502/503/504 在读取响应体前按状态码与响应头判定；响应体按块读取，每次底层读取以剩余预算做 select 等待，gzip 解码与 chunked 分帧等内部连续读取同样受总预算约束，单次阻塞读取也以剩余预算作为 socket 超时；响应首部与响应体共用同一请求总预算，首部/连接/TLS 的阻塞读取按剩余预算收紧并在连接后校验，超预算同样按 `network_timeout` 中断；DNS 解析与纯 CPU 解析不受硬中断，6/8 秒是目标上限而非绝对保证。连接阶段超时视为请求尚未发出，可安全恢复扫描；读取超时或已发送但结果未知的提交仍按待确认处理。调度以学校服务器时间校准本机时钟偏差。429 严格按 `Retry-After` 等待，收到 429 或带等待值的过载响应后先等待，再发起历史探测或其他业务请求；两个后台只读线程与主线程共用这一等待截止点：每轮扫描先吸收两个线程的服务端等待、检查共同截止时间，再决定是否（重）启动后台线程，启动函数内部也会在未到期时直接停止返回；退避期间同时暂停活动列表与后台历史线程，冷却都钳到共同截止时间（取最长等待），恢复后各自按冷却重启；502/503/504 时同样短退避，服务端有效等待要求优先；非法或不可持久化的等待值使用本地退避，不写入无限等待。启动后（认证前）加载 OCR 模型，避免首次提交才加载；取图与识别耗时写入本地诊断。开抢前约 2 秒（`SEU_PREWARM`，默认开启）用主会话查询一次“我的活动”，刷新历史缓存并保持验证码／提交连接热度；该查询替代稍后才会发生的历史刷新，不额外叠加长期请求；请求超时上界取 `min(1.5 秒, 距开抢剩余时间 − 0.1 秒)`，保证不会阻塞到开抢之后；距开抢剩余不足 0.4 秒时直接跳过预热、不发起请求；失败不阻塞提交，需要服务端等待时仍按原退避处理，其他失败只记录诊断。开抢前约 0.6 秒（`SEU_CAPTCHA_PREFETCH`，默认开启）取图并识别，候选出现后直接提交；只在开抢时刻前触发，开抢后不再预取；请求超时上界取 `min(0.6 秒, 距开抢剩余时间 − 0.03 秒)`；距开抢剩余不足 0.45 秒时跳过预取，预热结束后重新计算剩余时间再决定是否预取；超时或失败时回退为现场取图；预取结果超过 5 秒未用则丢弃并现场取图，被服务端判为验证码错误时回退现场取图重试（诊断 该次列表请求耗时`，作为可能的最早开抢时间，不再用固定 2 秒上限兜底；余量超过 2 秒（`PREPARATION_MAX_UNCERTAINTY`）时跳过预热、验证码预取与可选对齐，并记录诊断 `preparation_skipped`（`reason=clock_uncertainty`，按开抢场次去重），候选仍可现场取图提交；估算按稳定学校开抢时间戳固定，重算只允许向更早移动，永远不会把准备截止点后移。预热、验证码预取与开抢对齐的目标取下一场尚未开放的场次；当前仍在快轮询窗口的旧场次不会挡住后续场次的准备。开抢窗口内使用独立会话（复制已登录 cookies）后台只读轮询活动列表，目标间隔 0.10 秒；主循环只消费 0.75 秒内的快照；快照过期但后台轮询正在请求时，先等待最多 0.3 秒的轮询完成事件，若后台仍在请求，再等待最多 6 秒复用该请求，仍不可用才同步回退（等待的是该过期快照之后的新版本，而不是上次已消费版本，两段等待合计上界约 6.3 秒），服务端等待与错误仍优先；后台轮询运行期间，开抢等待期内主循环等待后台轮询的完成事件（成功或失败都通知）而不是一次睡满整个间隔，且只对已消费快照版本之后的新轮询完成生效，旧通知不会导致空转，版本读取与清除之间完成的轮询也不会被漏掉；快照与版本号在同一把锁内读取，不会出现旧数据配新版本，不增加请求；服务端 429／`Retry-After`、过载等待与本地退避仍优先，事件不能绕过。开抢对齐是可选实验项（`SEU_POLLER_ALIGN`，默认关闭）：开启后主循环把按学校时钟校准的下一个开抢时刻交给后台轮询做一次性对齐，让某一次轮询落在开抢时刻附近，最多把该次等待延长到两倍轮询间隔且不增加请求；但学校时钟 `xtdqsj` 处理仅为防御性措施，证据与更正见[使用指南](usage.md#开抢与拥塞恢复)。
- 候选可用性按学校前端同款判定：发布状态、预约时间窗（以学校服务器时间为准）、已约人数与总人数（满员即跳过）；不再调用不可靠的预约前检查接口。提交结果以提交响应与按活动 ID 核对为准。

- 首次登录的网关连接可按配置回退一次备用 IP，触发条件及限制见[网关回退](usage.md#网关回退)；不重放预约请求、不降低证书校验。

## 状态与恢复

- 同一状态目录通过文件锁限制一个实例；同账号在其他机器或浏览器版的实例须由用户停止。
- 正常启动始终认证并重查学校进度，即使本地任务已完成：仍达标就结束且不重复通知，不足则恢复扫描，再次达标时通知。
- `--new-task` 仅为重新核对已完成任务的兼容入口，不额外多约一场，不允许重置扫描或待确认任务。
- `--resolve-pending` 是待确认提交的人工兜底入口：停止运行中的实例后使用；只读查询“我的活动”，原场已出现则确认成功，未出现时必须由操作者显式输入确认短语才清除待确认与待确认占位；取消不改变状态；不发送提交请求。正常自动处理不依赖该命令。
- 重启保留待确认提交、待确认核对次数、待确认占位、冷却和退避；学校时间尚未校准时，保留并继续拦截已有冷却，不按本机时间判定到期；后续列表或慢路径复核缺少学校时间时沿用已知偏差。版本 1 单场任务自动迁移到版本 2 的目标任务。损坏状态、通知历史、非法恢复时间或账号不符时保留原文件并停止，不用新快照覆盖错误。
- 状态采用原子替换和持久化写入；健康快照为观察用途，写入在等待边界按 phase 变化或约 1 秒节流刷新，退出前强制刷新；`authentication`、`captcha`、`submitting`、`confirming`、`manual_required`、`failed`、`done`、`waiting_for_attendance` 阶段进入前以及错误、邮件状态变化会立即写入 phase 与状态，因此普通等待下 `--status` 最多滞后约 1 秒，关键阶段进入时 phase 立即可见，但 `updated_at` 可能滞后到该请求结束；待确认前持久化、确认、占位与重试时间等关键状态仍同步落盘。错误退避时同时暂停活动列表与后台历史刷新线程，两者冷却都钳到共同服务端等待截止时间（取最长等待），恢复后各自按冷却重启。停止、SIGTERM 和 Ctrl+C 保留任务并释放锁，不取消预约。强制终止、断电无法保证退出通知。
- 从待确认恢复扫描时先建立替代占位，再清除待确认字段，确保中断退出保存的状态仍有保护。状态升级和人工解除按活动 ID 保留其他预约的新旧格式占位，不整批清除。
- `--status` 离线显示本地状态及快照时效，不以 PID 文件或 `scanning` 判活；任务锁、阶段和成功查询时间共同提供运行证据，不能代替学校结果。
- `--check` 与扫描共用字段校验和筛选，展示逐场标题、首个原因及预约时间；不使用本地冷却，不创建任务、不做状态升级，不提交、取消或发邮件。正常扫描的私有诊断快照跨重启保留；旧快照标注时间，不为诊断额外查询。
- 当前列表的必要筛选详情仅留在本地状态与终端，不进入事件日志或邮件，不保存完整个人历史。
- 私有诊断写入状态目录的 `diagnostics.jsonl`：扫描节奏、筛选变化、验证码、验证码预取、开抢前预热、提交、核对结果、快照确认、自动解除、待确认占位、预约关键步骤失败；提交记录含取图、OCR、连接建立耗时、候选数据年龄（`rows_data_age`）、提交前落盘耗时（`precommit_save_seconds`）及验证码来源（`prefetch`／`fresh`），扫描节奏记录活动列表来源（`poller` 快照或 `query` 同步查询）、快照年龄、列表请求耗时（`rows_fetch_seconds`）、数据年龄（`rows_data_age`）、主循环请求数与后台轮询次数；后台历史刷新命中和格式非法回退分别记录 `history_background_used`／`history_background_invalid`，余量过大跳过准备记录 `preparation_skipped`（`reason=clock_uncertainty`）；字段脱敏、只追加，不进入终端、邮件或事件日志；后台只读线程失败被主循环回收时记录一次 `background_reader_stopped`（`reader`、固定原因码或异常类名、`server_directed`、服务端要求等待秒数 `retry_seconds`，仅本地诊断；服务端要求的失败通常先被共享等待路径吸收、可能不产生该行）；正常启动时若 `diagnostics.jsonl` 超过 8 MiB，先改名为 `diagnostics-<YYYYmmdd-HHMMSS>.jsonl`（重名加数字后缀），保留全部旧文件、不删除，运行期间不轮转；`--check` 不轮转也不写诊断。

## 邮件与告警

- 邮件是唯一主动通知渠道，可关闭；关闭后仍记录终端和本地事件。只读检查不校验邮件配置；独立 `--test-mail` 只发一封测试邮件，不访问学校或修改任务。
- `qq.com`、`163.com`、`126.com`、`gmail.com` 按域名精确匹配，大小写不敏感；仅需完整邮箱地址及授权码或应用专用密码，默认发给自己。非空显式主机、端口、发件人与收件人优先；其他域名需手动配置。
- 邮件字段全空或缺省时关闭，仅保留 `SMTP_PORT=465` 也关闭；部分配置不完整或无效则报错停止启动。使用校验证书的隐式 TLS，兼容无需认证的 TLS 中继；不增加明文、STARTTLS 或 OAuth。
- 只在重大问题尝试通知：需要人工认证、连续五分钟无法完成查询、连续五分钟无法完成验证码或提交请求（预约关键步骤失败）、可捕获异常退出、程序异常退出；预约成功通知受 `SEU_MAIL_SUCCESS` 控制，开启时每次经活动 ID 确认的预约成功发送一封，由后台线程发信、不阻塞扫描，关闭时不发；不发目标完成、待确认、恢复通知或日报。通知失败不改变预约结果，不触发重复预约。
- 同一未解决告警在发信前保存，跨重启只尝试一次；失败或结果不明不自动重发；问题解决后出现新问题可重新告警；恢复只记录，不再发信。关闭邮件不消费新的持久邮件配额。
- 持续查询失败从首次失败起计时，满五分钟后尝试通知一次；等待期间照常重试，告警不延后业务查询或退避；开抢窗口内延后到窗口结束再发送，期间恢复则不发送；查询恢复不发送恢复邮件。验证码或提交请求的连续失败单独计时（列表查询成功不清除），满五分钟通知一次；提交返回可判定结果、预约成功或不再有候选时视为恢复；同在开抢窗口内延后并去重，恢复不发送恢复邮件。
- 邮件使用中文说明和处理建议，包含最近核对的已选听、待参加、类别缺口、数据及查询时间、安全错误码和检查计划；未知进度不能写成零。不含讲座标题、学校凭据、验证码、票据或完整活动记录。
- 重大告警使用同步 SMTP，记录发送事件、实际耗时与固定错误分类，跨重启保留最近结果；成功通知复用 SMTP，但在后台守护线程发送，不更新重大告警的邮件历史字段。进程退出不等待成功通知线程，尚未完成的邮件可能中止；不自动补发，不输出异常原文、SMTP 响应或邮件地址。SMTP 接受和收件箱送达分别判断。2026-10-29 19:00 的成功通知已由用户确认在收件箱收到；程序日志只在发送失败时记录 `notification_failed`，无法独立观察成功通知的送达，送达结论以用户确认为准。
