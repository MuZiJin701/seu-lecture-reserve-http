### 开抢初期的同步刷新与候选发现延迟

诊断时间线显示：

- 19:00:01.986 的一轮扫描触发了同步历史刷新：
  - `mine_seconds ≈ 1.232s`
  - `activities_seconds ≈ 0.596s`
  - `history_reused = false`
- 下一次 `selection_changed` 为 19:00:05.040。

原因是当时开抢快窗口沿用的历史缓存有效期为 30 秒；从 18:59:31 进入快窗口开始计算，缓存在 19:00:01 左右过期，正好在开放瞬间触发了一次“我的活动”同步查询。之后将缓存有效期改为 60 秒，并保留“开抢前正常轮询刷新历史”的行为，避免在开放瞬间因 30 秒过期而阻塞列表/提交。

需要区分证据边界：日志证明该轮历史刷新占用约 1.23 秒，也证明 19:00:05 的筛选变化记录中线上已满；筛选快照只在变化时记录，不是逐请求完整抓包，因此不能将全部五秒延迟归因于这次刷新，更不能证明 19:00:00–19:00:05 之间线上名额曾经可约。线上竞争命中率仍需后续开抢实测。

从 19:00:05.040 记录候选，到 19:00:07.221 第一次开始提交，还经过约 2.18 秒。该档案没有独立的取验证码／OCR 分段耗时，不能把这段全部归因于模型或网络。开抢前约十秒的已记录扫描耗时约 0.32–0.44 秒；本次开抢窗口事件没有记录 429、502/503/504 或网络超时，不能作为重度过载恢复已通过的证据。

### 预约成功后为什么卡住

新预约在“我的活动”中首先返回：

```
FBZT=1, SFDK=0, SFWY=None（缺失）
```

当时的 `progress()` 要求 `SFDK`/`SFWY` 都必须是 `0/1`，因此把缺失的 `SFWY` 判为未知，任务持续 `attendance_status_unknown`，无法继续预约其他目标。

修复后：尚未结束的预约缺少打卡/违约字段时按“未参加、未违约”处理并计入待参加；已结束记录仍未知才暂停。

### 邮件

本次运行发生在“预约成功邮件”功能启用之前；当时按原策略只发送重大告警，不发送成功通知。19:05 的 `query_failure` 因处于开抢窗口被延后，此后进程被停止，未观察到该邮件送达。

后续版本已支持 `SEU_MAIL_SUCCESS=true`：每次按活动 ID 确认的预约成功会发送一封邮件，并由后台线程发送，不阻塞扫描。历史本次预约不会补发邮件。
