# 开放前准备、我的活动刷新和参考目标

11 月 4 日双账号开抢时，取图和我的活动查询失败，两账号均未提交。已移除缺乏实际收益证据的对齐，按阶段查询；TCP 完成后用剩余预算约束 TLS 握手。最新策略与此前验证见[验证状态](../acceptance/2026-11-05-prep-history-goal.md)。

## 当前取舍

- **我的活动刷新不在提交路径中等待。** 只在登录／重新认证、进入快抢期预热、待确认核对、预约确认成功后刷新，单次预算统一为 8 秒。首次可靠结果仍是冲突检查的基础。快抢期只通知一次，发现候选和提交前不额外刷新。学校侧手动变化不会立即反映，可重启账号同步。
- **统一使用运行机器的时钟。** 列表查询阶段、我的活动预热、验证码预取、预约时间窗判断和占位期限使用同一时钟。学校提供公布的预约时间窗、发布状态和名额。排程准确性依赖系统时钟同步，依据见[时钟测量与排程验证](../acceptance/2026-11-05-prep-history-goal.md#时钟测量与排程验证)。预取目标仍为公布的开放时间前 2.7 秒，单次预算和结果有效期均为 8 秒。各阶段的预算和有效期见[查询策略](../thread-query-strategy.md#各阶段查什么)。
- **只有 429 或有效 `Retry-After` 触发共同等待。** 列表或我的活动收到无等待指令的 HTTP 502–504 时，在本线程短退避。取图失败按尝试额度重试。临时网络、响应格式或 OCR 问题、超时和验证码判错都走正常节奏。我的活动查询失败继续同一次刷新事件。提交结果不明时仍先核对，保留占位保护。
- **参考目标只用于展示。** 按有效预约计数，不要求打卡，达标后继续预约；学校认定另行判断。

具体时段与线程分工见[查询策略](../thread-query-strategy.md)，操作见[使用指南](../usage.md)，规则见[需求](../requirements.md)。
