## 本场暴露的问题

### 1. 网络连接与我的活动数据可靠性阻断了提交

我的活动预热没有失败：两账号发出预热请求后，均采用了新产生的可靠快照。失败的是开抢后的后续我的活动查询；新错误会使当前结果不可用于新增，即使此前缓存尚未到十秒有效期，也不据此继续提交。

A2 预取预算约 0.569s，在 TLS 阶段耗时约 0.589s 后失败；两个账号现场取图随后均耗尽约八秒预算，未进入可用于提交的 OCR 结果阶段。两者我的活动查询从开放后约三秒起连续失败，先出现响应头等待，随后主要是 TLS/TCP 等待；约两分十秒恢复。

开抢附近诊断共记录 A1 26、A2 29 条失败，计入 `suppressed` 后至少对应 57、58 次失败，其中两账号我的活动查询各至少 56 次。没有观测到 429/Retry-After 或明确认证失效，不能将网络失败认定为学校主动限流、服务器过载或账号会话互踢。

线程改造确实使主线程能先响应其他结果：A1 在 19:00:03.414、A2 在 03.768 因我的活动查询错误退出验证码等待，取图任务则到 08.808/08.970 才最终失败并被回收。这里 `captcha_error` 记录可能来自我的活动线程错误，不能直接当成验证码接口已经失败的时间；应按 `request_failed.reader/endpoint/stage` 区分。

补充核对：我的活动预热不只是发出请求，A1 在 **18:59:56.930**、A2 在 **18:59:57.264** 都采用了新的可靠结果。它使用独立的我的活动 Session，不会同时预热验证码/提交所用的主 Session。之后首次我的活动查询失败分别在 19:00:03.411/03.766，阶段为响应头等待；后续重试才主要表现为 TLS/TCP 超时。预热成功只能证明当时查询可用，不能保证下一次请求仍正常。

验证码准备方面，A1 没有预取启动记录，A2 预取未完成 TLS，均未产出可用预取结果。取图部分尝试 TCP 约 10ms 已完成、TLS 却耗尽预算，这支持将故障定位到握手等待阶段；没有当时的握手报文或学校端日志，无法进一步区分上游握手处理、链路丢包或中间设备影响。双账号同时失败、随后恢复只能提示共同路径异常，不能证明具体根因。

### 2. TCP 到 TLS 的剩余预算交接存在可复现缺口

多个我的活动查询请求配置两秒预算，实际耗时约 3.04–3.09s。例如 A2：TCP 1.066s、TLS 2.023s，总计 3.091s。

在本机隔离复现 `_DeadlineHTTPSConnection.connect` 时，构造 socket 让 TCP 消耗一秒，进入 TLS 时 socket 超时仍为两秒，最终共耗时三秒。该次部署没有在 TCP 成功后收紧 TLS 预算，连接结束后的截止检查无法提前结束正在等待的握手。该缺口已在后续版本修复（TCP 完成后按剩余预算收紧 TLS）。后续修复见[当前验证状态](2026-11-05-prep-history-goal.md)。

按[火山引擎普通公网 IP 规则](https://docs.volcengine.com/docs/elastic-ip-address/bandwidth-faq?lang=zh)，配置带宽限制出网；不超过 10Mbps 时默认入网为 10Mbps。两兆比特约为每秒 250KB，并不一定同时限制学校响应的入网。该实例实际 EIP/共享带宽绑定尚未通过控制台核实。

本场主要故障发生于 TLS 握手和响应头等待，而非已观察到的响应体传输耗时。带宽排队/丢包仍可能影响握手，因此不能只凭故障阶段排除它；需要结合 19:00 附近 EIP 出入带宽与限速丢包指标判断，暂不据此认定升级带宽能解决。原始统计仅在忽略目录 `state/evidence/2026-11-04/server-bandwidth-sar.json`。

## 验证码线程能否使用独立会话

**可以独立持有客户端 Session，但学校端校验能否跨会话互通尚未验证，不宜直接替换。**

| 设计 | 判断 |
| --- | --- |
| 当前借用主业务会话 | 取图与提交沿用同一 Cookie/连接池；本场线程交接正常，但取图受 TLS 故障阻断 |
| 独立 `requests.Session`，复制认证 Cookie | 可隔离客户端连接与可变状态；仍须处理 Cookie 更新、认证代次、验证码单任务和提交一致性。复制 Cookie 不证明学校端状态也独立 |
| 独立登录会话取图、原会话提交 | 是否有效不能由拿到图片判断；必须有学校真实校验成功证据，本场没有这样的提交样本 |

Requests 的 Session 管理 Cookie 和连接池，见[官方说明](https://requests.readthedocs.io/en/latest/user/advanced/#session-objects)。新建 Session 不会自动消除 TLS 握手故障，还可能使提交失去预取连接的复用机会。本项目取图返回图片、提交发送活动 ID 与验证码，未携带独立 challenge ID；从接口形状看，不能假定任意登录态之间可共享验证码，具体绑定仍需学校实测。

优先修复连接剩余预算，并测试现有写会话能否更早建立可复用连接、现有预取是否应前移及调整预算；再评估独立会话。若要独立，保留单任务、认证代次和 Cookie 一致性要求，在可操作测试活动上验证真实校验。此次没有额外取图、实验性提交或架构变更。
