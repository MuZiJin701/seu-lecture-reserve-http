# 2026-10-31 审查修复：运行中保存、请求体上限与并发登录限速

本记录对应 2026-10-31 审查提出的三个问题。三者均先本机复现，再修复并补回归；业务规则见[需求](../requirements.md#页面与部署)，运行说明见 [Web 指南](../web.md#管理员登录)。

## 1. 运行中的 Web 账号无法保存配置

**复现**：用真实子进程模拟管理台自己的工作进程（持有该账号 `task.lock`），调用 `Manager.update` 修改名称，返回 `state_in_use`，名称未写入。原因：上一轮为拒绝外部 CLI 写入而增加的锁检查没有区分锁的归属，把管理台自己运行中的工作进程也当成外部 CLI。

**修复**：只有在本进程没有该账号存活工作进程、且检查点锁仍被持有时才拒绝（外部 CLI）；管理台自己的 worker 持锁时继续走原有安全停止、写入和重启流程。停止后、写入前再复查一次锁，避免停止与外部 CLI 抢锁之间写入分叉。

**回归**：真实子进程持有检查点锁时保存成功、名称与 `revision` 已更新、账号仍在运行；外部 CLI 持锁时仍返回 `state_in_use`（既有用例保留）。

## 2. 64 KiB 请求体上限可绕过

**复现**：向本机 Uvicorn 发送 `Content-Length: 1` 且 `Transfer-Encoding: chunked` 的登录请求，实际正文 131,133 字节，返回 **200**。原因是校验只信任声明的 `Content-Length`，而 h11 按分块传输读取正文。

**修复**：新增 ASGI 请求体限制中间件，对非 GET 的 `/api/*` 按**实际接收字节**累计并回放已读请求体，超过 64 KiB 立即返回 413（`request_too_large`），不依赖客户端声明长度；原 `Content-Length` 缺失 411、声明超限 413 的快速校验保留。

**回归**：本机 Uvicorn + 原始 socket 发送分块超限请求返回 413 且含 `request_too_large`；正常 JSON 登录往返（既有真实 Uvicorn 用例）仍通过。413 后连接可能被重置，测试已按平台行为容忍。

## 3. 并发登录可突破失败次数限制

**复现**：12 条同来源并发错误密码请求，全部执行了 PBKDF2 校验（12 次），0 次限速；文档约定每来源每分钟 5 次。原因是预算检查与失败计数不在同一临界区，请求可在计数写入前全部通过检查。

**修复**：登录在计算哈希前原子预留一个校验名额（每来源与全局都计入未完成名额），完成后统一结算：失败计入来源预算并释放名额，成功清除该来源失败记录并释放；异常路径也释放名额，不会泄漏。

**回归**：12 条同来源并发错误密码恰好 5 次进入校验并返回 `login_rejected`、7 次 `login_rate_limited`，哈希调用 5 次，结束后无未结算名额。既有顺序限速、成功清除来源、全局 100 上限用例保留。

## 边界与未验证

- 修复 1 的极端竞态：管理台停止 worker 后、写入配置前若外部 CLI 恰好取得检查点锁，会在写入前复查并拒绝，但复查与写入之间仍有极小窗口；未用真实 CLI 与 Web 同时操作复验。
- 修复 2 只限制应用层收到的字节；未验证不同 Uvicorn／h11 版本对 `Content-Length` 与分块冲突的处理，也未处理慢速分块（slowloris）与连接层超时；这些不属于本次三个问题。
- 修复 3 依赖单管理进程内存状态；项目固定一个 Web worker，不覆盖多进程共享限速（当前不支持多 worker）。
- 本轮未重启正在运行的管理服务，也未做真实浏览器或攻击流量验证；真实学校链路与本次改动无关。
